# System Rules

Load this file only for architecture, runtime, ownership, state, persistence, or security work.

## Ownership

- **O1 MUST — Single authority.** One normative owner defines each semantic responsibility. Other documents/components reference or derive from it; conflicts are ownership/spec defects, not precedence problems.
- **O2 MUST if the architecture has multiple semantic owners — Owner graph.** Treat architecture as a graph of semantic owners and dependencies; top-level docs map the graph instead of redefining its details.
- **O3 MUST — Reuse before create.** Before adding a manager, registry, store, dispatcher, service, UI primitive, or persistence representation, find the existing owner. If it is too narrow, generalize or redesign it instead of adding a parallel layer.
- **O4 MUST — No parallel authority.** Do not add a second path that decides the same meaning. Temporary adapters/bridges are justified only when they connect genuinely different contracts; owner-adjacent patch budget defaults to zero.
- **O5 SHOULD — Prefer change locality.** A semantic change should mostly stay inside the boundary that owns it. If unrelated layers require coordinated edits, re-check the boundary.
- **O6 MUST when independent replacement/removal matters — Contract-mediated coupling.** Components depend on public semantic contracts, not each other's internals.
- **O7 MUST when optional modules/features are claimed — Minimal configuration conforms.** The smallest/empty composition must still have a valid lifecycle.
- **O8 MUST for extension/plugin ecosystems — Open extensions, closed laws.** Separate extensible surfaces from system-wide laws such as identity, ordering, authority, commit, and failure.
- **O9 MUST when a standard extension path and escape hatch coexist — Extend before escape.** Improve the canonical extension surface before routing ordinary features through a bypass.
- **O10 MUST when extensibility/modularity is claimed — Add/remove/replace/compose.** Extensibility means all four, not merely adding features.
- **O11 SHOULD unless subsystems truly have independent deploy/security/lifetime/data boundaries — Prefer composable primitives.** Do not create a global subsystem per feature when common semantic primitives can express the behavior.
- **O12 SHOULD — Physical boundaries need real independence.** Create crates/packages/services for independent consumers, public APIs, security/unsafe isolation, heavy dependency isolation, or process/deploy boundaries—not merely because a concept is large. Avoid responsibility-free common/shared/utils/misc buckets.

## Abstraction

- **A1 MUST — Require independent evidence.** Promote a shared abstraction only when two independent consumers/cases use the same contract without bypasses, or when it implements a genuine closed-domain law. For runtime/provider/substrate abstractions, a second materially different implementation is preferred evidence before an implementation-ready claim.

## Runtime semantics

- **S1 MUST — Make dependencies and ordering explicit.** Never let registration/source/container order, thread completion, callback timing, or hidden mutable wiring determine semantics.
- **S2 MUST when access/dependencies/capabilities are declared ahead of time — Declared access equals runtime access.** Runtime must not silently widen the declared graph or authority.
- **S3 MUST when state has multiple representations/replicas — Separate authority from projections.** Distinguish canonical truth, durable evidence, working state, materialized projection, cache/index, runtime binding, and external observation instead of treating them as interchangeable state. In centralized models, keep one semantic truth plus rebuildable projections/caches/indexes; duplicate representations require an explicit derivation or validation law. In distributed models, explicitly define replica identity, merge/conflict law, and causal authority.
- **S4 MUST — Close the semantic matrix.** For important contracts, resolve every applicable dimension: identity, ownership, state, transition, authority, ordering, visibility/atomicity, failure, cancellation, retry/idempotency, replay, persistence, reconfiguration, concurrency, unknown/opaque handling, observability. Mark only genuine non-applicability as N/A.
- **S5 MUST when structural validation is possible — Reject knowable defects early.** Missing/ambiguous dependencies, illegal scope, incompatible schema, and similar deterministic defects should fail at compile/bind/validation rather than hide behind runtime first-match, fallback, or retry.
- **S6 MUST when observable transaction/publish/durable boundaries exist — Explicit commit boundaries.** Do not conflate commits with different semantics.
- **S7 MUST when async/external results can affect authoritative state — Canonical ingress.** Callbacks/workers/providers return through the owner's ingress/result/transaction boundary instead of mutating authoritative state directly.
- **S8 MUST for remote operations or external effects — Local cancellation is not an external terminal.** If the external outcome is unknown, represent it as indeterminate/unknown.
- **S9 MUST for replay/recovery/event sourcing — Replay recorded semantic evidence.** Reproduce recorded inputs/decisions/generation evidence; do not re-run already published external effects or reread live nondeterministic sources. Recovery uses durable/current evidence instead of guessing a nearby state or unconditionally restarting from zero when stronger evidence exists.
- **S10 MUST when incremental behavior is an architectural requirement — Incremental by construction.** Model change units, dependencies, invalidation, and reuse from the start rather than bolting optimization onto full recomputation.
- **S11 MUST when versioning/opaque extensions/partial knowledge exist — Preserve unknowns.** Keep unknown, absent, empty, unavailable, opaque, malformed, unsupported, conflict, failed, and indeterminate distinct whenever behavior differs. Do not map unknown schema/variant/owner/evidence to guessed defaults or nearest known cases; define preservation, upgrade conditions, and forbidden operations. Preservation is not interpretation.
- **S12 MUST — Performance does not justify semantic bypass.** Optimize within canonical ownership, authority, commit, isolation, and validation boundaries.
- **S13 MUST when multiple authoring/front-end/API surfaces produce the same system — Lower to one model.** Convenience surfaces compile/lower into the same canonical declarations/contracts instead of creating a second semantic runtime.
- **S14 MUST when physical execution can restart or multiply — Separate semantic and execution identity.** Path, PID, thread, pointer, connection, OS handle, discovery position, and process-local identity are not logical operation/object/principal/generation identity. Do not mint durable identity for transient or derived state before the domain requires it.
- **S15 MUST when restart/reconfiguration/provider replacement exists — Names do not prove identity or state carry.** Define identity and carry explicitly.
- **S16 MUST when topology is fixed during compile/bind — Freeze topology.** Running code must not re-open manifest/catalog/name lookup to add hidden wiring; topology changes require an explicit reconfiguration contract.
- **S17 MUST — Separate independently varying semantic axes.** If identity, equality, state, authority, lifetime, representation, or execution placement can vary independently, model them as independent axes before defining composite types. Collapse axes only when a closed domain law requires the coupling.
- **S18 MUST when equality affects behavior — State the equality basis.** Define whether equality means exact bytes, normalized form, field semantics, digest equality, or stable identity. Do not substitute a convenient partial field or implementation-local surrogate.
- **S19 MUST when fallbacks, defaults, bounds, or timeouts affect observable behavior — Give policy an owner.** Such values are contract inputs or owned policy with a resource, threat, or semantic rationale; providers do not invent hidden constants. A fallback must not create semantics that no owner specified.
- **S20 MUST when an authority target is derivable from the request — Derive it from canonical request data.** Do not keep a second contradictory target field, interpret an action/service name as a broad permission alias, or manufacture an arbitrary runtime selector.
- **S21 MUST when public contracts cross implementations or substrates — Keep semantic contracts substrate-independent.** Public identity, wire meaning, authority, and lifecycle must not depend accidentally on native ABI layout, pointer/process identity, or one host implementation. The execution substrate materializes semantic decisions; it does not become a second semantic authority.
- **S22 MUST — Conceptual grouping is not runtime topology.** A family, category, namespace, or documentation group does not by itself create a manager, principal, generation, store, process, compiler, or lifecycle. Add runtime topology only when an owned contract requires it.
- **S23 MUST when physical operations implement semantic transactions — Separate semantic and substrate atomicity.** A semantic transaction/commit claim and the atomicity of a file, rename, database call, IPC write, or other substrate primitive are distinct guarantees. Do not infer one from the other.
- **S24 MUST when lifecycle phases differ — Model lifecycle events separately.** Request acceptance, work completion, presentation, acknowledgement, and resource release are distinct events when their lifetimes differ. Long-lived entity activity belongs in an event/watch/lifecycle contract rather than a request forced to have a misleading terminal.
- **S25 MUST for retry, recovery, restart, or reconfiguration — Close operation and generation identity.** Define operation identity, deduplication owner, evidence retention, indeterminate behavior, carry/disposition, transition commit, and stale-result handling. Late results remain attributed to their origin lifetime/generation and never silently attach to a replacement.
- **S26 MUST when wall time and elapsed time both exist — Keep time axes separate.** Use monotonic time for elapsed durations and wall/civil time for calendar instants. Do not subtract wall-clock observations and treat the result as monotonic elapsed time.
- **S27 MUST when source/build preparation exists — Separate preparation from target composition/runtime.** Resolve, fetch, build, verify, and seal artifacts in a preparation trust stage; the target runtime consumes prepared descriptors/artifacts rather than source-language or builder internals. Preparation policy and application/runtime policy remain distinct.

## Data and security

- **T1 SHOULD when users own durable portable content — User data outlives product metadata.** Preserve generally representable user content even if product-specific metadata or the product disappears.
- **T2 MUST for shared/external/multi-writer artifacts — Conflict-aware writes.** Compare expected identity/revision/digest with current state and surface conflicts instead of silently overwriting another writer.
- **X1 MUST when claiming sandbox/isolation/trust tiers — Security terminology matches enforcement.** Never describe in-process/native execution as sandboxed or isolated unless the actual authority boundary enforces that claim.
- **X2 MUST when external or untrusted peers provide identity-bearing data — Bind security identity from trusted evidence.** Principal, session, route, origin, actor, or security identity comes from authenticated routing/binding/transport evidence owned by a trusted coordinator or broker, not from a self-asserted payload.
